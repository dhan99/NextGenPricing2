# Branching & PR Strategy

The 32-week refactor uses **trunk-based development with short-lived feature branches**. This document is the rulebook.

## Branches

| Branch      | Purpose                                              | Protection |
|-------------|------------------------------------------------------|------------|
| `main`      | Always deployable. Mirrors what's live in stakeholder demos. | Required PR review, required passing CI, no force-push |
| `develop`   | Integration branch. Merges land here first.          | Required passing CI |
| `feat/<id>-<slug>`     | Short-lived feature branch (≤5 days).        | None |
| `refactor/<id>-<slug>` | Short-lived refactor branch (≤5 days).        | None |
| `fix/<id>-<slug>`      | Hotfix branch (≤2 days).                      | None |

`<id>` is the backlog ID from `docs/refactoring/BACKLOG.md` (e.g. `F1.1`, `F0.5`). `<slug>` is a short kebab-case description.

**Examples**:
- `feat/F1.1-multi-entity-tabs`
- `refactor/F1.4-extract-deal-aggregate`
- `fix/F1.4-domain-event-bus-restart-issue`

## Flow

```
                   (after demo)
   feat/X ──┐                   ┌──> main ──> stakeholder demo
            ├── PR ──> develop ─┤
   feat/Y ──┘                   └──> (auto-deploy to staging)
```

1. Branch from `develop`.
2. Push frequently. Open the PR early (mark as Draft) so CI runs.
3. When ready, mark Ready for Review. CI must be green.
4. At least one approving review.
5. Squash-merge into `develop`. Delete branch.
6. After a stable demo cycle, fast-forward `main` from `develop`.

## What goes in a PR

Every PR must:

- **Reference an issue.** PR title format: `<id>: <one-line summary>`. Example: `F1.1: Add multi-entity tabs above scope step`.
- **Pass the smoke test.** `bash scripts/audit/smoke_test.sh` must exit 0.
- **Pass CI.** Lint, typecheck, tests.
- **Move the calc-parity needle in the right direction.** If the change touches pricing, the calc-parity golden test must still pass. If it intentionally changes pricing behavior, the PR description must state that and link to the regenerated golden.
- **Update docs that drift.** If the PR adds tables, update `docs/audit/schema_inventory.csv`. If it adds endpoints, update `docs/audit/api_inventory.csv`. (Both are auto-regenerated by the extractor scripts — running them is part of the PR checklist.)
- **Be small.** A PR that touches more than ~500 LOC across non-trivial files is too big. Split it.

## What does NOT go in a PR

- **Schema changes mixed with feature changes.** Schema changes are their own PR (additive only — see migration policy below).
- **Refactor + feature in the same PR.** If you're moving code AND adding behavior, split it. Reviewers can't catch regressions in a 2,000-line diff.
- **Replit-specific code.** Anything that only works on Replit gets flagged and put on the AWS-migration backlog instead. See `docs/audit/REPLIT_COUPLINGS.md`.

## Migration policy

The 42 existing tables are **load-bearing**. The Strangler Fig refactor only adds; it does not subtract until the new code has fully replaced the old.

Rules:

- **Additive migrations only** in Phase 1. New tables, new nullable columns. No drops, no renames, no `NOT NULL` on existing columns.
- **Backfill scripts are required** for any new column that downstream code will read. Don't ship a column and a code change that reads it without filling old rows.
- **Backups before migrations.** Even on dev: `pg_dump` to a file before `drizzle-kit push`. The script `scripts/audit/backup_db.sh` (to be created in F0.4) does this.
- **Migrations run in CI/CD against staging first.** Before any prod migration, the same migration must have run cleanly against staging within the last 24 hours.

## Demo discipline

`main` is what the next stakeholder demo runs against. The "is `main` demo-ready?" question has a binary answer:

- ✅ Wizard goes from Setup → Summary without errors
- ✅ Approval gate triggers at the right thresholds
- ✅ Calc parity holds
- ✅ Auto-push to integration adapters fires on approval
- ✅ All five `/api/ai/*` heuristics return non-empty responses
- ✅ Autonomous-agent draft from a Dynamics opportunity completes in <10 seconds

If any of these is broken, `main` is not demo-ready, and the responsible PR is reverted, not patched. Patching at 10 PM the night before a demo is how trust gets lost.
